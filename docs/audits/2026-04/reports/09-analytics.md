# Analytics — Audit Report

## TL;DR (REQUIRED — exactly 5 bullets, max)

- API signature mismatch: `SentimentAnalysisEngine.analyze_sentiment(text, source)` is called with `(ticker, list[dict])` from `RecommendationEngine._run_sentiment_analysis`, causing a runtime `AttributeError` on the `str.get()` call when iterated — this breaks every live recommendation.
- `OptimizedRecommendationEngine._scan_market_optimized` calls `scanner.scan_market_streaming(...)` which does not exist on `MarketScanner`; the optimized daily-recommendations path raises `AttributeError` unconditionally at runtime.
- `StockRecommendation` dataclass has no `ranking_score` field; `rank_recommendations` and `rank_recommendations_optimized` set it via dynamic attribute assignment on a frozen-like dataclass, which silently succeeds in Python but is semantically wrong and breaks static analysis/serialisation.
- `DCFModel.sensitivity_analysis` mutates `self.terminal_growth_rate` in a loop, leaving the object in a corrupted state after each call — a correctness bug in the valuation subsystem.
- Seven economic constants are hardcoded in source (`risk_free_rate=0.045`, `market_risk_premium=0.08`, `portfolio_size=100_000`, `max_weight=0.02` Sharpe stop, etc.) with no configuration layer; these should be injected or read from config.

## 5. Risk-Prioritized Punch List (top 10)

1. **F-09-001** — Sentiment engine signature mismatch — every recommendation that reaches the sentiment analysis step crashes at runtime; high blast radius.
2. **F-09-002** — `scan_market_streaming` missing on `MarketScanner` — the entire `OptimizedRecommendationEngine` daily pipeline is non-functional.
3. **F-09-003** — DCF `sensitivity_analysis` mutates `self.terminal_growth_rate` — corrupts valuation object state silently; any code that calls `sensitivity_analysis` before `calculate_intrinsic_value` produces wrong valuations.
4. **F-09-005** — `EnhancedStockRecommendation` error path raises `TypeError` — the error-recovery path is itself broken, masking root causes in production.
5. **F-09-004** — `ranking_score` dynamic attribute lost during serialisation — ranked order is not preserved in any output that goes through `asdict`.
6. **F-09-010** — `PortfolioOptimizer.optimize` ignores constraints and always returns equal weights — the entire MPT efficient frontier computation is a no-op.
7. **F-09-014** — Incorrect ADF test statistic — cointegration pair detection results are statistically unreliable.
8. **F-09-007** — Johansen test silently delegates to Engle-Granger — API users cannot distinguish between methods.
9. **F-09-008 / F-09-009** — Hardcoded economic constants (risk-free rate, portfolio size) — correctness degrades over time as rates change; position sizes are meaningless for non-$100K portfolios.
10. **F-09-015 / F-09-016** — O(n²) SMA and loop-based OBV/AD — material performance bottleneck in 500-stock batch jobs.

## 6. Open Questions

- Q1: Should `SentimentAnalysisEngine.analyze_sentiment(text, source)` be the canonical single-text entry point and `analyze_stock_sentiment(ticker, texts)` the bulk entry point? The current naming implies they are at the same level of abstraction but they are not. The team should decide and document the public API surface.
- Q2: Is `PortfolioOptimizer` in `backend/analytics/portfolio/modern_portfolio_theory.py` intended to coexist with `backend/utils/portfolio_optimizer.py` (which has a full scipy-based solver), or is the analytics version a redundant duplicate that should be deleted? If the latter, `recommendation_ranking.optimize_recommendations` should call the utils version directly.
- Q3: The `CointegrationAnalyzer.confidence_level` attribute (default `0.05`) is documented as "statistical significance level" but used as `p_value < self.confidence_level`, which is correct for a significance threshold — however the field name is confusing (0.05 is alpha, not confidence). Should it be renamed to `significance_level` to match the `backtest_var` parameter convention used in `VaRCalculator`?
- Q4: `EnhancedStockRecommendation` in `hybrid_engine.py` inherits from `StockRecommendation` (a frozen-style dataclass) and adds optional fields via `@dataclass`. Since Python's `@dataclass` inheritance requires all parent required fields before child optional fields, there may be hidden `TypeError` issues with field ordering that only surface when the `__post_init__` fails. Full integration test needed.
