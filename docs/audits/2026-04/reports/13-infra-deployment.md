# Infrastructure & Deployment — Audit Report

## TL;DR

- Two parallel Dockerfile lineages (`Dockerfile.backend` at repo root vs `infrastructure/docker/backend/Dockerfile{,.optimized}`) diverge on Python version (3.12 vs 3.11), TA-Lib source (SourceForge vs GitHub), build targets (no `target` vs `runtime`/`development`), and security posture. `docker-compose.production.yml` references `target: runtime` which exists only in `infrastructure/docker/backend/Dockerfile.optimized`, but `dockerfile: ./Dockerfile.backend` (root) — production builds will fail.
- Production nginx healthcheck targets `/nginx_status` (docker-compose.production.yml:291) which is restricted by `allow 127.0.0.1; deny all;` in nginx.optimized.conf:283-289 — the curl from inside the container hits the listening socket on `localhost` so it usually works, but `/nginx_status` is only defined in the HTTP (port 80) server block; the HTTPS (443) block has only `/health`. Mixed misconfig depending on which conf is loaded.
- `infrastructure/cdn/cloudflare_config.yaml` is full of placeholder strings (`yourdomain.com`, `your-server-ip.com`, `admin@yourdomain.com`) and an incorrect CNAME content type (a CNAME cannot point to an IP). Not deployable as-is.
- `docker-compose.yml` bind-mounts source code into running services (`./backend:/app/backend`, `./frontend/web:/app`) even though the file is the base for production composition — production overlay does not unset these volumes, so the immutable image is shadowed by host code at runtime.
- Secrets handling weak across the stack: `Dockerfile.ml-api`, `Dockerfile.ml-monitoring`, `Dockerfile.ml-scheduler` `COPY .env* ./` baking env files into the image; the root `.dockerignore` excludes `.env` but explicitly re-includes `!.env.example` and `!.env.*.example`, leaving real `.env.<env>.example` patterns ambiguous.
