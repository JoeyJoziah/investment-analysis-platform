# Airflow Data Pipelines — Audit Report

## TL;DR (REQUIRED — exactly 5 bullets, max)

- `ml_training_pipeline_dag.py` uses four Airflow 1.x operator imports (`PythonOperator` from `python_operator`, `BashOperator` from `bash_operator`, `ExternalTaskSensor` from `external_task_sensor`, `days_ago` from `utils.dates`) that raise `ImportError` on Airflow 2.x, preventing the DAG from loading at all.
- `ml_training_pipeline_dag.py` references `np.random.randn` in `evaluate_models` without importing `numpy`; the function will crash at runtime with `NameError: name 'np' is not defined`.
- `ml_training_pipeline_dag.py` calls `checker.check_recent_data_quality(...)` on `DataQualityChecker`, a method that does not exist in `backend/utils/data_quality.py`; this broken import will silently skip training or raise `AttributeError`.
- `enhanced_stock_pipeline.py` runs `VACUUM ANALYZE` via `pg_hook.run()` inside an implicit transaction; PostgreSQL forbids VACUUM inside a transaction block, causing the cleanup task to fail with `ProgrammingError`.
- All three DAGs use the deprecated `schedule_interval` parameter; on Airflow 2.4+ this raises a deprecation warning and on 3.x will break — `schedule` is the correct keyword.

## 4. Cross-Scope Linkages

- `F-06-002` → scope `03-ml-engine`: `evaluate_models` calls `monitor.calculate_metrics` from `backend/ml/pipeline/monitoring.py`. The stub data issue is partly in the ML engine's `ModelMonitor` interface. Real test predictions must be persisted at training time in scope 03 to be consumable here.
- `F-06-003` → scope `11-backend-utils-shared`: `DataQualityChecker` in `backend/utils/data_quality.py` needs a new method `check_recent_data_quality` to satisfy the DAG contract. Scope 11 owns that file.
- `F-06-008` → scope `03-ml-engine`: The placeholder evaluation logic is a symptom of missing model artifact storage during training. Scope 03 (ML engine) must store held-out predictions in the registry for scope 06 to retrieve them.
- `F-06-012` → scope `15-test-suite`: The broken test import path means these tests are likely excluded from the CI test run. Scope 15 should add this directory to the pytest collection path.
- `F-06-015` → scope `07-database-persistence`: Column naming in `technical_indicators` (`ema_12`, `ema_26`) misleads consumers. A table comment or column rename should be coordinated with scope 07.

## 5. Risk-Prioritized Punch List (top 10)

1. **F-06-001** — Airflow 1.x imports in `ml_training_pipeline_dag.py` — The ML training DAG cannot load on any Airflow 2.x deployment. This is a zero-cost silent failure (DAG simply disappears from the UI with an import error in `dag_processing.log`).
2. **F-06-003** — `DataQualityChecker.check_recent_data_quality` does not exist — Even after fixing F-06-001, the first task of the ML pipeline will fail with `AttributeError`, permanently blocking model retraining unless manually resolved.
3. **F-06-002** — Missing `numpy` import in `evaluate_models` — Even after fixing F-06-001 and F-06-003, model evaluation crashes at runtime with `NameError`, meaning no model ever gets deployed via this pipeline.
4. **F-06-008** — Placeholder random data in model evaluation — The model "selected" for production is chosen on noise. This is a data correctness / model quality risk that compounds silently even once F-06-002 is fixed.
5. **F-06-006** — `airflow.utils.db.create_session` removed in Airflow 2.3+ — `daily_stock_pipeline.py` will fail to parse on current Airflow, blocking all daily stock data ingestion.
6. **F-06-004** — VACUUM inside transaction block — The cleanup task in `enhanced_stock_pipeline.py` fails every run with `ProgrammingError`, meaning the database is never vacuumed by this pipeline and table bloat accumulates.
7. **F-06-005** — `schedule_interval` deprecated — All three DAGs will break on Airflow 3.x upgrade; low urgency today but a one-line fix now avoids migration pain later.
8. **F-06-009** — Placeholder alert email `ml-alerts@company.com` — Failure alerts are silently dropped or delivered to an unintended destination.
9. **F-06-007** — ~270 lines of dead code in `daily_stock_pipeline.py` — Cognitive load and maintenance risk; low urgency but high cleanup value.
10. **F-06-013** — `data_count >= 20` vs. `MIN_DATA_POINTS = 26` threshold inconsistency — Produces silently incorrect EMA-26 values for ~200-500 tickers with short price history, skewing MACD and therefore recommendations.

## 6. Open Questions

- Q1: What Airflow version is deployed in production? The severity of F-06-001, F-06-005, and F-06-006 depends on whether Airflow 2.x or 1.x is running. If 1.x, the import issues are non-issues but dynamic task mapping (Airflow 2.3+) used in `daily_stock_pipeline.py` will fail instead.
- Q2: Is the `enhanced_stock_pipeline` (`enhanced_stock_pipeline.py`) intended to run in parallel with `daily_stock_pipeline`? Both target the same `price_history` and `technical_indicators` tables and both schedule at `0 6 * *`. Concurrent writes with overlapping tickers could cause lock contention or duplicate processing. Intent should be documented and one pipeline designated authoritative.
- Q3: The `ml_training_pipeline_dag.py` references `http://ml-api/{model_name}` as the deployment endpoint (line 557). Is this internal DNS resolvable from Airflow worker nodes? No connectivity check or fallback is present.
- Q4: `aggregate_fetch_results` computes `estimated_parallel_time` via `max(batch_id) * 10` (line 1155-1156), which is meaningless as a throughput denominator. Was this intended as a real metric? If so, actual wall-clock time should be tracked via `time.time()` around the dynamic mapping group.
