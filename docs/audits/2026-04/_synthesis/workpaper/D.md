## §1 Executive Summary

Every ML-driven investment recommendation, backtest, performance record, alert, system-health metric, live price tick, and feature-drift signal that the platform surfaces in production is generated by `random.uniform()` / `random.randint()` / `np.random.*` or by `Dummy{LSTM,XGBoost,Prophet}` classes, with **no `mock=True` flag, no `data_source: "simulated"` annotation, and no startup health gate**. For an SEC-regulated investment platform whose own disclosure text (`recommendation_service.py:25-31`) warns about data freshness, shipping fabricated values as authoritative output is simultaneously a correctness bug, a user-trust failure, and a compliance exposure.

The five findings in this cluster span both the service layer (F-02-003, F-02-015, F-02-018) and the ML layer (F-03-003, F-03-005). Two are critical (F-02-003, F-03-003), one is high (F-03-005), two are medium (F-02-015, F-02-018). The fix is **policy-dependent** rather than purely technical: the platform must decide whether unavailable models should return synthetic placeholders, refuse to respond, or surface an explicit "no recommendation available" state. Per the synthesis-handoff §6 question, the recommended default is to refuse (HTTP 503 + structured `model_unavailable` payload + Sentry breadcrumb) and let the frontend render an explicit empty state, but this decision has SEC implications and **MUST be human-acked before Loki applies it**.

## §3 Recommended Fix Steps

### §3.1 Policy decision — REQUIRES HUMAN ACK (blocking)

Before any code change, the platform owner must answer **synthesis-handoff §6**: *"Should the platform return 'no recommendation available' instead of random values?"* The audit asserts this is an SEC-implicated decision and Loki MUST halt at this gate.

**Recommended default (per cluster sub-plan):**
1. When a model is in `Dummy*` fallback or feature data is insufficient, the endpoint returns **HTTP 503 Service Unavailable** with a structured body: `{"error": "model_unavailable", "model": "<name>", "reason": "binary_missing" | "insufficient_data" | "fallback_active", "request_id": "..."}`.
2. A Sentry breadcrumb tagged `model_unavailable` is emitted with the model name and the originating endpoint.
3. The frontend handles the new error state with a "No recommendation available — model retraining in progress" empty-state component (touches scope 12; see §8 cross-cluster).
4. A startup health gate (`GET /health`) reports `fallback_models: <count>` and the deployment readiness probe fails if any production-critical model is in fallback.

**Alternative (must be explicitly ack'd):** Continue returning synthetic values but tag every payload with `data_source: "simulated"` and `_DEMO_DATA = True`, gated behind `settings.DEMO_MODE`. Lower compliance bar but preserves UX continuity for demo environments.

### §3.2 Code-level steps (after ack)

1. **F-03-003 first** — Either run the full training pipeline to produce `xgboost_model.pkl`, `lstm_weights.pth`, Prophet `.pkl`, OR set `HF_AUTO_DOWNLOAD=true` and pull from HF Hub. Add startup probe in `model_manager.py:199-211` that fails fast (or marks unhealthy) when all models are in fallback.
2. **F-02-003** — Audit each call site listed in the finding (`admin_service.get_system_health_data`, `admin_service.list_users`, `recommendation_service.run_backtest`, `recommendation_service.generate_performance_records`, `recommendation_service.generate_alert_history`, `portfolio_rebalancing.generate_performance_data_points`, `socketio_service._stream_price_updates`). Per call site, either (a) replace with real implementation (system metrics → `psutil`; user list → DB query; alerts → DB query) or (b) gate behind `settings.DEMO_MODE` and return HTTP 501/503 in production.
3. **F-02-018** — In `analysis_service.py:316-327`, change the short-circuit branch to raise `InsufficientDataError` instead of returning hardcoded `{beta: 1.15, alpha: 0.02, sharpe_ratio: 1.85, …}`. Caller handles the exception and surfaces the same `model_unavailable` 503.
4. **F-03-005** — In `feature_store.py:666-668,743-754`, replace `np.random.normal(0,1,1000)` and `np.random.randint(1000, 10000)` with real queries against the SQLAlchemy `db_engine` already initialised in `__init__`. If the feature table is empty, raise `InsufficientDataError`; do not fabricate.
5. **F-02-015** — Pick one transport (recommend Socket.IO for proxy-friendliness). Delete the loser. Document the choice in `docs/architecture/`. Update frontend WS client to a single URL. Note this fix must land **after** F-02-003 in either transport — fixing one transport's random-data emitter while the other still ships fake data leaves the bug present.

## §6 Risk & Blast Radius

- **SEC / compliance (CRITICAL):** Platform ships fabricated investment recommendations with no disclosure. Even one external user acting on a random `recommendation_service.run_backtest` output is potential securities-fraud exposure.
- **User trust:** Once a user notices that two consecutive `/system/health` calls return wildly different CPU values with no real load change, all admin telemetry credibility evaporates.
- **Alert fatigue / false signals:** F-03-005 means drift alerts fire on noise; SREs train themselves to ignore them, masking real drift when it occurs.
- **Dual-transport amplification (F-02-015):** Fixing the random-data emitter in only one of `websocket_service.py` / `socketio_service.py` is a silent regression — clients on the other transport still receive fake data.
- **Test fragility:** Existing tests likely pass against random fallbacks because assertions are loose (e.g., `assert "cpu_percent" in resp`). Adding the fail-first tests in §4 raises the floor.
