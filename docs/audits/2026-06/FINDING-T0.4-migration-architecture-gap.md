# FINDING — T0.4: Alembic migration chain cannot build a fresh DB (architecture gap)

> **Status:** ESCALATED · HUMAN-GATED decision (call it **D7**, not anticipated by the PRD)
> **Date:** 2026-06-23 · **Branch:** `loki/state-remediation-2026-06`
> **Context:** Surfaced while executing PRD task **T0.4** (`docs/audits/2026-06/PRD-loki-state-remediation-2026-06.md`).

## TL;DR

The three `#242` drift bugs named in T0.4 are **fixed and verified** (commit `68f3b7e`).
But the PRD's T0.4 acceptance — *"from an empty database, `alembic upgrade head` exits 0"* —
**cannot be met by those fixes**, because the migration chain is architecturally incoherent:

1. **No initial-schema migration.** The lowest revision `001_critical_indexes` (`down_revision = None`)
   *adds indexes to* `price_history`, `stocks`, etc. — but **no migration ever creates those base tables.**
   The base schema is built only by `Base.metadata.create_all` (app startup `init_db()` →
   `backend/utils/database.py`, and `backend/utils/db_init.py`). So `alembic upgrade head` on a
   truly empty DB dies immediately at 001.
2. **Migrations duplicate `create_all` objects without `IF NOT EXISTS`.** Once `create_all` has built
   the model-defined indexes, migration 001 re-creates several of them with raw `op.create_index`
   (no `if_not_exists`), so `upgrade head` then fails with `relation "idx_..." already exists`.
   Migration `010` likewise re-`create_table('investment_thesis')`, which `create_all` already built.

Net effect on the real deploy (`production-deploy.yml` runs `alembic upgrade head` in a one-off job):
- **First deploy to an empty prod DB → crash at 001** (base tables missing).
- **Re-run against a `create_all`'d DB → crash on duplicate index** (path "B" below).

Fixing this fully is a **coordinated schema decision** (initial-schema migration + idempotency
reconciliation) that should be **reviewed by Devin**, not authored autonomously in a remediation pass
(loki escalation rule: major-refactor / architecture → human checkpoint).

## What T0.4 actually fixed (committed, verified)

`68f3b7e` — three surgical `#242` correctness bugs that crash the upgrade regardless of the above:
- `001`: `idx_stocks_active` referenced `is_tradeable`; real column is `is_tradable`.
- `008`: `idx_stocks_sector` indexed `stocks(sector)`; `stocks` has only `sector_id` (FK) → repointed.
- `008`: `idx_recommendations_confidence_desc` partial predicate used `CURRENT_TIMESTAMP` (STABLE,
  illegal in an index predicate) → dropped the time clause.

These are unambiguous correctness fixes and stand on their own.

## Reproduction (disposable `timescale/timescaledb:2.14.2-pg15`)

```bash
# DATABASE_URL → disposable pg ; dummy SECRET_KEY/JWT_SECRET_KEY/REDIS_URL for settings import
# Path A — truly empty DB:
alembic upgrade head
#   -> psycopg2.errors.UndefinedTable: relation "price_history" does not exist   (at 001)

# Path B — app's real bootstrap, then migrate:
python -c "from backend.models.unified_models import Base; \
           from sqlalchemy import create_engine; \
           Base.metadata.create_all(create_engine(DATABASE_URL))"
alembic upgrade head
#   BEFORE 68f3b7e: column "is_tradeable" does not exist                         (at 001)
#   AFTER  68f3b7e: relation "idx_api_usage_provider_time" already exists        (at 001, dup index)
```

So `68f3b7e` advances Path B past the three `#242` crash points; the remaining wall is the
`create_all`/migration duplication.

## Recommended fix (D7 — pick one; Devin's call)

- **Option A (recommended): author a `000_initial_schema` migration** generated from `Base.metadata`,
  repoint `001.down_revision = '000_initial_schema'`, and make migrations `001`+ idempotent
  (`if_not_exists=True` on `create_index`, `if_exists=True` on `drop_index`, `if_not_exists=True` on
  `create_table`). Then `alembic upgrade head` builds a fresh DB end-to-end and `create_all` can be
  dropped from the runtime path (single source of truth = migrations). *Risk:* the autogenerated
  initial schema must exactly match what `001–010` (and the TimescaleDB hypertables in `002`) expect —
  needs careful review; this is why it is human-gated.
- **Option B (smaller): keep `create_all` as the schema source; make all migrations idempotent only.**
  `create_all` + `upgrade head` then works (subsequent deploys), but a *truly empty* `upgrade head`
  (CI `migration-check.yml`, first prod deploy) still needs `create_all`/`stamp` first — so CI's
  fresh-migration test must be changed to `create_all` then `upgrade`/`stamp`, not bare `upgrade head`.
- **Option C: `create_all` + `alembic stamp head`** on first init (migrations never run on a fresh DB,
  only on existing deployments going forward). Lowest code change; abandons "migrations build the DB".

`alembic alembic-check` / CI `migration-check.yml` (T2/W5) should be reconciled to whichever option is chosen.
